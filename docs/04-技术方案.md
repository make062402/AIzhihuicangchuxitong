## 2. 关键技术方案

### 2.1 计费规则引擎

**问题**：不同货物、库位、时段的租金不同，需要灵活匹配且可预测。

**方案**：四级精细度匹配 + 同层取最新。

```
匹配优先级：L1（物品+库位）> L2（仅物品）> L3（仅库位）> L4（通用）
```

匹配 SQL 核心逻辑：

```sql
SELECT * FROM billing_rules
WHERE active = 1
  AND (start_date IS NULL OR start_date <= :outboundDate)
  AND (end_date   IS NULL OR end_date   >= :outboundDate)
  AND (item_id     IS NULL OR item_id     = :itemId)
  AND (location_id IS NULL OR location_id = :locationId)
ORDER BY
  CASE WHEN item_id IS NOT NULL AND location_id IS NOT NULL THEN 3
       WHEN item_id IS NOT NULL THEN 2
       WHEN location_id IS NOT NULL THEN 1
       ELSE 0 END DESC,
  id DESC
LIMIT 1
```

- `ORDER BY` 的 CASE 表达式实现了"越精细越优先"的层级；
- 同层冲突时 `id DESC` 保证取最新规则；
- 未匹配到规则时回退到默认价（¥0.5/天，min_days=1）。

### 2.2 FIFO 批次分配 + 存放天数计算

**方案**：出库时按 `inbound_date ASC, id ASC` 顺序遍历该型号剩余批次，逐批扣减。

```
take = min(剩余需求, 该批次 remaining_qty)
days = max(出库日期 - 入库日期, 计费规则 min_days)   // 至少 1 天
fee  = take × days × price_per_day
```

- 用**事务**包裹整个出库流程，保证批次扣减与费用写入原子性；
- 出库前先校验总库存，不足直接 400 拦截，避免部分扣减。

### 2.3 认证与权限

**认证**：密码用 `bcrypt.hashSync(password, 10)` 加盐；登录成功签发 JWT（payload 含 id/username/role），前端存 `localStorage`，axios 请求拦截器自动附带 `Authorization: Bearer <token>`。

**授权**：中间件两层

```
authRequired  —— 校验 JWT，挂载 req.user
adminRequired —— 校验 req.user.role === 'admin'
```

- 写操作、管理接口挂 `adminRequired`；
- 出库等业务接口挂 `authRequired`；
- 前端 `ProtectedRoute` 做界面级守卫，后端中间件做真正的安全边界。

### 2.4 环境变量校验

**方案**：启动时用 zod schema 校验 `process.env`，非法配置直接 `process.exit(1)`，避免运行期才暴露错误。

```ts
const envSchema = z.object({
  NODE_ENV: z.enum(['development', 'production', 'test']).default('development'),
  PORT: z.string().transform(Number).default('3000'),
  CORS_ORIGIN: z.string().refine(...).default('*'),
  RATE_LIMIT_WINDOW_MS: ...,
  RATE_LIMIT_MAX_REQUESTS: ...,
})
```

### 2.5 单容器一体化部署

**方案**：Dockerfile 多阶段构建。

1. **builder 阶段**：分别 `pnpm install --frozen-lockfile` 并构建后端（`tsc`）与前端（`vite build`）；
2. **runtime 阶段**：仅 `pnpm install --prod` 装生产依赖，拷贝 `backend/dist` 与 `frontend/dist`（→ `/app/public`）；
3. **后端托管前端**：`app.ts` 检测 `public/` 目录，存在则 `express.static` 托管 + SPA 路由回退（非 `/api` 请求都返回 `index.html`）。

**收益**：一个镜像 + 一条命令 `docker compose up -d` 即可运行，客户无需技术背景。

### 2.6 多租户隔离方案

**方案**：一客户一部署（物理隔离）。

| 维度 | 隔离方式 |
| --- | --- |
| 容器 | 每客户独立 `wms-<tenant>` 容器 |
| 数据库 | 独立 `wms.db` 文件，挂载到 `/data/wms/<tenant>/` |
| 网络 | 独立端口（8001 起自动分配）或独立域名 |
| 密钥 | 每客户独立随机 `JWT_SECRET`（`openssl rand -hex 32`） |

由 `new-tenant.sh` 脚本自动完成上述配置。

### 2.7 数据备份方案

**方案**：`backup.sh` 脚本 + crontab 定时。

- 优先用容器内 `sqlite3 .backup` 做在线一致性备份；
- 无 sqlite3 时回退到直接拷贝 db 文件；
- gzip 压缩，按租户归档到 `/data/wms-backups/<tenant>/`，保留最近 30 天。

### 2.8 库存预警算法

**方案**：单条聚合 SQL 计算每个物品的库存、最老批次天数，结合阈值判定 4 类预警。

```sql
SELECT i.id, ...,
  COALESCE(SUM(r.remaining_qty), 0) as stock,
  COALESCE(MAX(julianday('now') - julianday(r.inbound_date)), 0) as oldest_days,
  COALESCE(t.low_threshold, 50)  as low_threshold,
  COALESCE(t.high_threshold, 2000) as high_threshold,
  COALESCE(t.aging_days, 60)  as aging_days
FROM items i
LEFT JOIN inbound_records r ON r.item_id = i.id AND r.remaining_qty > 0
LEFT JOIN stock_thresholds t ON t.item_id = i.id
GROUP BY i.id
```

判定逻辑：

```
stock == 0                        → out_of_stock
stock < low_threshold             → low
stock > high_threshold            → high
oldest_days >= aging_days && stock > 0 → aging
```

## 3. 数据库迁移策略

**方案**：`CREATE TABLE IF NOT EXISTS` 保证幂等；对已有库做**轻量迁移**（`PRAGMA table_info` 检测缺失列 + `ALTER TABLE` 补列），例如旧版 `priority` 数值列迁移为 `priority_level` 枚举。

## 4. 风险与权衡

| 权衡项 | 决策 | 代价 |
| --- | --- | --- |
| SQLite vs PostgreSQL | 选 SQLite | 无多进程并发写，高并发写场景需谨慎 |
| 单容器 vs 微服务 | 选单容器 | 水平扩展受限，但交付门槛极低 |
| 同步 SQL vs ORM | 选同步 SQL（better-sqlite3） | 少了 ORM 抽象，但代码直观、性能好 |
| JWT vs Session | 选 JWT | 无法服务端强制下线（登出需前端删 token） |
